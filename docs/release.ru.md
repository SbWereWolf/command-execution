# Раздельный выпуск CE

Один push стабильного тега `vX.Y.Z` запускает npm и PyPI для одного коммита.
Версии тега, Python-модуля, `pyproject.toml` и npm-манифеста сверяются.
Каждый канал собирает, публикует и проверяет свой артефакт. Поэтому один
канал может завершиться успешно, даже если весь запуск Actions отмечен
как ошибочный из-за второго канала.

## Переиспользуемый workflow

[Вызывающий workflow](../.github/workflows/publish.yml) дважды вызывает
[общий workflow](../.github/workflows/reusable-release.yml). Сборки передают
свои артефакты как `release-npm` и `release-pypi`. Задание Trusted Publishing
для PyPI остаётся в вызывающем `publish.yml` и ждёт только Python-артефакт.

При подключении EM или WR владелец публикующего репозитория указывает
полный SHA общего workflow в `uses` и передаёт repository variables через
`with` своего вызывающего workflow. В таблице приведены значения CE при
отсутствии переменных.

| Переменная | Вход общего workflow | Значение CE |
| --- | --- | --- |
| `RELEASE_PACKAGE` | `package` | `command-execution` |
| `RELEASE_DRIVER` | `driver` | `.github/scripts/release-channel.sh` |
| `RELEASE_PYTHON_VERSION` | `python_version` | `3.15` |
| `RELEASE_NODE_VERSION` | `node_version` | `24` |
| `RELEASE_NPM_VERSION` | `npm_version` | `11.21.3` |
| `RELEASE_NPM_ENVIRONMENT` | `npm_environment` | Пустое значение для издателя npm без окружения |

Вызовы также задают `channel` и `mode`. Драйвер в `.github/scripts/`
получает фазу, канал и абсолютный каталог результата. Workflow передаёт
`RELEASE_MODE`, `RELEASE_PACKAGE`, `RELEASE_REF_NAME`, `RELEASE_SHA` и
`RELEASE_PYTHON`. Фаза `prepare` строит и проверяет артефакт и пишет
`manifest.json`. Фаза `artifact` сверяет SHA коммита, тег, версию, канал и
хеш файла перед выдачей пути. `registry` определяет, нужна ли публикация,
а `verify` сверяет реестровые дайджесты. Фазы `identity` и `qualify-build`
сверяют проверочный тег и собирают его дистрибутив. Фаза `qualify` получает
четвёртым аргументом каталог с артефактом сборки и публикует этот файл в
отдельный проверочный реестр. Для подключения EM и WR их драйверы должны
реализовать этот интерфейс для собственных пакетов.

Оба вызова общего workflow делегируют `contents: read` и `id-token: write`,
поскольку Actions проверяет права вложенных заданий до вычисления их условий.
Задания сборки и квалификации работают с `contents: read`. OIDC используют
задания публичной публикации со стабильного тега.

Перед публичным выпуском сверить регистрации Trusted Publisher с
вызывающим файлом `publish.yml`. Для PyPI используется GitHub environment
`pypi`. Для npm значение `RELEASE_NPM_ENVIRONMENT` должно соответствовать
регистрации издателя. Квалификационные прогоны подтверждают работу каналов
в тестовых реестрах. Доступ к публичным реестрам проверяется отдельно.

## Происхождение npm-поставки

[`npm/wheelhouse.lock.json`](../npm/wheelhouse.lock.json) фиксирует версии,
адреса источников и SHA-256 колёс из `npm/wheelhouse`. При обновлении
зависимости обновите колесо и запись вместе, сверив метаданные и лицензию.
Лицензии сохранены внутри колёс.

У npm собственные входы сборки. Сборка проверяет каждое колесо по lock и
собирает колесо CE с закрытым Python-индексом. В `vendor/` готового
npm-архива входят колесо CE, runtime-колёса, их контрольные суммы и сведения
о происхождении runtime-зависимостей. Сборочные инструменты используются
на этапе упаковки. Чтобы установить SDK из npm без Python-индекса,
используйте [пример для потребителя](../npm/README.md#python-sdk-from-an-npm-installation)
с версией CE из его npm lock.

Python-поставка использует зависимости из [`pyproject.toml`](../pyproject.toml).
При обычной установке pip разрешает их из настроенного Python-индекса.
[Выбор версии и проверка установки](maintenance.md) описаны в инструкции
сопровождения.

## Проверочные выпуски

Создайте и отправьте два квалификационных тега одного коммита.

- `qualify-ce-vX.Y.Z-pypi-outage`
- `qualify-ce-vX.Y.Z-npm-outage`

Для нового кандидата можно добавить ревизию перед именем реестра, например
`qualify-ce-vX.Y.Z-r2-pypi-outage` и `qualify-ce-vX.Y.Z-r2-npm-outage`.
Существующие теги сохраняют связь с исходными запусками.

Каждый тег запускает обе цепочки с изолированными реестрами. На hosted
Ubuntu `sudo` создаёт сетевое пространство имён и поднимает loopback.
Сборка и публикация работают от пользователя runner без внешнего маршрута.

У обоих каналов сначала должно пройти задание `Build distribution`. Затем
в каждом запуске один канал успешно выполняет шаг `Qualify release`
с публикацией и чистой установкой, а второй получает на этом шаге ошибку
обращения к своему проверочному реестру. У успешного npm-канала архив публикуется в
Verdaccio, скачивается с проверкой SRI и устанавливается через npm. У
успешного PyPI-канала колесо публикуется через Twine в devpi, скачивается
с проверкой SHA-256 и устанавливается через pip. Оба канала проверяют CLI
и SDK. Ошибка подготовки runner, сборки или скачивания артефакта не
подтверждает отказ проверочного реестра.

Сопоставьте тег и SHA, ID запуска и номер попытки, ID заданий и архивы
`qualification-npm-<attempt>` и `qualification-pypi-<attempt>`. В каждом
архиве `report/operation.log` фиксирует команду, адрес и код выхода.
У успешной операции дополнительно сверяются `report/digest`, скачанный
файл и `report/install.log`. Сверьте SHA-256 ZIP с метаданными GitHub.
Проверить связанный манифест для двух запусков можно из корня checkout:

```bash
python3 -B tests/release/evidence.py "$manifest"
```

Здесь `manifest` — путь к JSON, который связывает сохранённые run/jobs API,
журналы, входы и артефакты обеих попыток. Схема проверки находится в
[`tests/release/evidence.py`](../tests/release/evidence.py).

## Восстановление после частичного выпуска

1. Определите по заданиям запуска, какой канал опубликовал пакет и прошла
   ли финальная сверка. Сохраните исходный артефакт, его `manifest.json` и
   реестровый дайджест успешного канала.
2. Устраните причину отказа и повторите задание отказавшего канала с
   артефактом того же тега и SHA. Перед повтором проверьте, что исходный
   артефакт доступен для скачивания. Успешный канал можно оставить в его
   подтверждённом состоянии.
3. Если версия уже появилась в реестре, workflow признаёт точный повтор
   только при совпадении байтов по дайджестам. Для npm сравнивается
   `dist.integrity`, для PyPI — имена и SHA-256 файлов. Такой повтор
   переходит к финальной сверке. При расхождении байтов занятая версия
   отклоняется, новый артефакт требует отдельного выпуска с новой версией.
   Ошибка доступа к реестру останавливает проверку. Публикация разрешается
   после ответа HTTP 404 на запрос метаданных этой версии.
